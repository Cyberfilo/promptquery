# PromptQuery end-to-end eval

Real-execution comparison of **naive LLM-with-full-schema** vs **PromptQuery** on a live Postgres database.

This eval answers the headline question: *does PromptQuery's schema retrieval actually beat a plain API call?*

## What it does

For each natural-language question in the suite, it runs **two pipelines** with the **same LLM**, the **same system-prompt template**, and the **same Postgres database**. The only structural difference:

| Pipeline | Schema sent to LLM | Safety guard |
|---|---|---|
| **Naive** | The entire schema, dumped into the prompt | None |
| **PromptQuery** | TF-IDF-ranked top-K + FK-graph expansion, capped at `--max-tables` | `sqlglot`-based SELECT-only validator |

Both pipelines generate SQL, which is then **executed against the live database**. Scoring is **execution-equality**: the row sets must match the result of the gold reference SQL (order-insensitive, as a set of tuples).

## Why execution-equality, not SQL-string match

Two queries that reference the same tables can return wildly different results because of a single wrong join key, filter, or aggregation. String-match scoring is too lenient. Execution-equality is the standard used by Spider, BIRD, and Spider 2.0 — it's the only score that says "this query *actually worked*."

## Why two configs (shop vs shop+200-noise)

The PromptQuery thesis is *"works on production schemas with hundreds of tables."* A 14-table benchmark cannot prove or disprove that claim because the entire schema fits comfortably in any modern LLM's context.

The padded config (`--pad 200`) injects 200 synthetic noise tables (`tmp_event_log`, `staging_audit_2023_q3`, etc.) into the schema dict passed to both pipelines. **The naive baseline now has to find the right ~14 needles in a 214-table haystack.** PromptQuery's retriever filters down before the LLM sees anything. This is where the gap should open.

## Running it

Prerequisites:
- Docker (Colima works on macOS)
- `OPENAI_API_KEY` in env
- `pip install openai` in the venv (already pinned in `pyproject.toml` `[openai]` extras)

```bash
# 1. Spin up Postgres + load schema + seed data
cd eval && docker compose up -d
PGPASSWORD=promptquery psql -h 127.0.0.1 -p 55432 -U promptquery -d shop \
    -f fixtures/shop.sql
PGPASSWORD=promptquery psql -h 127.0.0.1 -p 55432 -U promptquery -d shop \
    -f fixtures/shop_seed.sql

# 2. Run the comparison (back at the repo root)
cd ..
.venv/bin/python -m eval.end_to_end --model gpt-5.4 --pad 0 --pad 200

# 3. Teardown
docker compose -f eval/docker-compose.yml down
```

### Flags

| Flag | Default | Meaning |
|---|---|---|
| `--model` | `gpt-5.4` | OpenAI model ID |
| `--pad N` | none (= `--pad 0`) | Add N noise tables. Pass multiple times to run multiple configs. |
| `--limit N` | all | Run only the first N questions (smoke testing) |
| `--dsn` | `postgresql://promptquery:promptquery@127.0.0.1:55432/shop` | Connection string |
| `--out` | `eval/results.json` | Where to dump per-question raw outcomes |

## Cost & latency

GPT-5.4 single call against the 14-table prompt: ~2-3 seconds. With 200-noise padding: ~4-8 seconds.

Full suite: 25 questions × 2 pipelines × 2 configs = 100 API calls. Wall-clock: 5-15 minutes. Cost: a few dollars at GPT-5.4 prices.

## Failure modes worth knowing

Both pipelines can fail in distinct ways. The harness distinguishes them:

| Outcome | What it means |
|---|---|
| `safety-rejected` (PromptQuery only) | The validator caught a non-SELECT or dangerous-function call. **A success of the safety layer**, but counted as a question fail. |
| `exec error: ...` | The LLM produced SQL that referenced a hallucinated column/table, or had a syntax error Postgres rejected. |
| `llm error: ...` | OpenAI returned an error (rate limit, invalid model, etc.). |
| `empty SQL` | The LLM returned non-SQL prose only. |
| ✓ + matching row count | Real pass. |
| ✓ + different row count | Result-set mismatch — query ran but returned the wrong data. Counted as fail. |

## Reading the results

The harness writes `eval/results.json` with per-question raw outcomes including the actual SQL generated by each pipeline, the rows returned, the elapsed seconds, and the error string (if any). Diff that file between runs to see exactly what changed.
